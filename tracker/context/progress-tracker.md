- Task 17 amendment — free-tier pass: staying inside Neon Free and Vercel Hobby. Owner-directed, on top of the audit's caching sweep and the performance pass above.

  **The reframe, which changed what "optimise" meant here.** The brief proposed the usual levers (query count, payload size, indexes, pagination). Those matter, but they are not what decides this bill. Neon's Free plan meters **wall-clock time the compute is awake**: 100 CU-hours against a 0.25 CU floor is ~400 awake-hours/month (~13 h/day), scale-to-zero is fixed at five minutes and is not configurable on Free. So *any* single query costs a five-minute minimum, and the metric that matters is how many separate five-minute windows a day opens — not how heavy each query is. A shop open ~12 h/day with continuous POS activity already spends ~90 CU-hours before a single storefront visitor arrives, which is what made the storefront's contribution the thing to drive to zero, and the register the thing to keep at its 0.25 CU floor rather than let the autoscaler climb.

  **The single worst offender was one line.** `completeSaleAction` and `revalidateOrder` called `revalidateTag("products", "max")` / `revalidateTag("bundles", "max")` on **every sale and every order transition** — because a stock number moved by one. During business hours that destroyed the entire public catalog cache continuously, so the storefront was never warm and every visitor was a database wake. Stock-only mutations (POS sales, confirm/cancel/void, the order-item editors) no longer touch storefront tags; mutations that change what the storefront *says* — name, price, image, `isActive`, promotions — still revalidate immediately, as does the human-initiated `adjustStockAction`. What the storefront gives up is a stock number up to `STOREFRONT_REVALIDATE_SECONDS` old, which cannot oversell anything because `createOrderCore` re-checks availability against the live row before accepting an order.

  **One cached snapshot replaced the per-filter query family.** `listCatalogProducts` deliberately ran **uncached** for any `?q=` or price range (caching on a raw query string would mint one permanent entry per URL a visitor can invent), so every crafted URL went straight to Postgres — an open door from `robots.txt` to a five-minute wake, all night, for results nobody reads. Meanwhile `/catalog/[categorySlug]` × sort × stock produced ~6N independently-expiring entries. Now `getCatalogSnapshot()` (every active product, newest first) and `listCatalogBundles()` (every active box) are the only browse-path reads; category, search, price range and sort are pure functions in the new `src/lib/catalog-filter.ts`, filtered in memory. Home, catalog, every category, every search, every sort, both locales — one fill per 15 minutes. `STOREFRONT_REVALIDATE_SECONDS` went 60 → 900 for the same reason: at 60s a single visitor per minute holds the compute awake around the clock. Promo *expiry* was already handled client-side (`promo-countdown.tsx` + `postPromoPrice`), so the only genuinely clock-driven lag left is a scheduled promotion *starting* up to 15 minutes late.

  **Measured, not asserted.** The Neon driver's `fetchFunction` was instrumented and the same script run against a production build of the old code and the new one (instrumentation removed afterward):

  | | before | after |
  |---|---|---|
  | Warm the whole storefront (home/catalog/boxes, both locales) | 5 | 5 |
  | 5 repeat loads of `/fr/catalog` | 0 | 0 |
  | **10 never-seen bot search URLs** | **30** | **0** |
  | **7 loads across sorts / price filters / boxes** | **10** | **0** |

  Worth recording for whoever measures this next: **`next dev` does not reuse `use cache` entries at all** — every page load re-queried, which reads as a catastrophic regression and is purely a dev artifact. Only `next build && next start` answers this question.

  **Real transactions, and the deletion of the compensating-undo code.** `neon-http` cannot hold a transaction open, so a POS sale was ~20+ sequential HTTPS requests with a hand-written ledger of applied stock adjustments replayed backwards on failure — by some distance the most delicate code in the repo, and itself able to fail halfway and leave recorded stock permanently adrift. `src/db/client.ts` gained `withTransaction`, one pool-per-call over `drizzle-orm/neon-serverless` (already installed; Node 22+ supplies a global `WebSocket`, so no `neonConfig` and no new dependency). Reads and single-statement writes stay on `db` — a WebSocket handshake costs more than one HTTP round trip, so this is only for units that must interleave reads and branch on them. Converted: `completeSaleCore`, `createOrderCore`, `confirmOrderCore`, `advanceOrderStatusCore`, `cancelOrderCore`, `voidOrderCore`, all three order-item editors, and `createStaff`. **Deleted, not left dormant:** `AppliedAdjustment`, `reverseAdjustments`, `applySaleStock`, `releaseOrderStatus`, `decrementStockLines`' inline reversal loop, and the `DELETE`-in-a-catch-block rollbacks in `createOrderCore`/`createStaff`. A short line now throws `InsufficientStockError` and `ROLLBACK` does what all of that hand-simulated. `decrementStockLine`'s conditional `WHERE` stays — it is what makes the decrement safe against a concurrent register, which `READ COMMITTED` does not give on its own.

  **The one mechanism that had to change to survive a transaction.** `insertWithUniqueOrderCode` recovered from a code collision by catching the unique violation and retrying with a higher sequence. That worked *only* because each statement was its own `neon-http` request: inside a real transaction a constraint violation poisons the transaction, so every statement after it fails and there is nothing left to retry with. Replaced with prevention — `pg_advisory_xact_lock(hashtext(prefix))`, released automatically on commit *or* rollback, with no unlock path to forget. It serialises order-code assignment for the month across concurrent transactions, which at two registers is free. The same constraint is why both idempotency-retry lookups (`existingOrderResult`, `findSaleByIdempotencyKey`) now run on `db`, **outside** the aborted transaction; that rule is recorded in `db-errors.ts` alongside the cause-chain note. `sku.ts` keeps its retry and says why: its callers are not transactional.

  **The register stopped re-reading the shop after every sale.** Two things were doing it. `router.refresh()` plus `revalidatePath('/admin/pos')` re-ran `listPosCatalog` + `listPosQuickPicks` + `listPosCategories` after **every single counter sale** — the most repeated database workload in the shop, none of it needed to answer "what changed?". `completeSaleCore` now returns the levels its own decrements left behind (`decrementStockLine` returns the remaining qty instead of a row id) plus every active bundle's availability in one extra query — one query, not ten round trips, and no drift, since selling a component moves the availability of every box containing it and the client cannot derive that. Separately, `handleSelectSku` called `resolvePosItemAction` on **every tile tap** — a session read plus three SKU lookups plus a pricing query, ~7 round trips per item added to a basket, to learn something the client was already holding. `PosGridItem` gained the `productId`/`variantId`/`bundleId` identity it lacked (a variant tile only knew its *own* id, with no way back to the parent product), so a tap resolves from memory; the server action survives only as the fallback for a SKU created since page load. Not a trust boundary either way — `completeSaleCore` re-resolves and re-prices every line inside the sale transaction.

  **The session was read from Postgres several times per request.** Every gate resolves it independently and a single admin render passes through several — the protected layout, the page, then one per service call; the POS page did it five times. `getRequestSession` wraps the read in React `cache()`. This is deliberately *not* the `session.cookieCache` that `auth.ts` rules out: the scope is one request, so the user row is still re-read on the next one and revoking a permission still takes effect immediately.

  **Indexes (migration `0010`).** `order_items(order_id)` **was never indexed at all** — Postgres does not index a foreign key for you, and this column carries every order detail read, `recomputeOrderTotals`, the dashboard's top-products join, and the `ON DELETE CASCADE` a failed sale fires. Plus `stock_movements(created_at desc)` (the movements log defaults to no product filter, which the existing `(product_id, created_at)` composite cannot serve — and that table grows one row per line per sale, faster than anything else in the schema) and `orders(status, created_at desc)`, which supersedes `orders_status_idx`. `tests/db/index-check.test.ts` asserts all three exist and are chosen for their query shapes; it runs `EXPLAIN` under `set local enable_seqscan = off`, because on a dev branch with a handful of rows the planner correctly prefers a sequential scan and the naive assertion answers nothing.

  **Also.** `listPosCatalog`/`listPosQuickPicks` were bare `db.select()`, dragging `description_ar`/`description_fr` — the largest text columns in the schema — across the wire for every row, on the one page open all day at the counter; both now have explicit column lists (Neon meters 5 GB/month of egress alongside compute). `getEffectivePrices` takes an optional client so a sale prices from the same snapshot it writes into. `track("pos_sale_completed")` moved *outside* the transaction — a rolled-back sale must not appear in analytics as one that happened.

  **One deliberate behaviour change:** catalog sorting now sorts the full filtered set and caps at 200, where the SQL capped first — so "cheapest first" previously only ranked the 200 *newest* products among themselves. Identical below 200 products. Search still does not fold accents ("seyes" ≠ "Seyès"), matching what `ILIKE` did; the LIKE-wildcard escaping is gone because a literal `%` in a substring test is exactly what that escaping existed to produce.

It does not — the Vercel project has no Git repository connected at all, so the push landed on GitHub and nothing happened; every deployment this project has ever had is a CLI upload from someone's working tree (`npx vercel --prod`). Connecting the repo is worth doing and is not done.

## Architecture Decisions

- **Drizzle wraps the driver's error — any SQLSTATE check must walk the `cause` chain.** `drizzle-orm` throws a `DrizzleQueryError` (`"Failed query: …"`) carrying the real `NeonDbError` as `cause`; `code` and `constraint` exist only on the inner one. Three separate hand-rolled checks in this repo read them off the top-level object, so **none had ever matched** — which meant the unique-violation retries in `sku.ts` and `order-code.ts` were dead code the whole time, silently. Nothing surfaced it: it type-checks, it lints, and the failure mode is "the retry never fires", which looks exactly like "there was no collision". Found only when a new test deliberately raced two inserts on the same unique key and got the raw driver error back. Now one `isUniqueViolation` in `src/lib/db-errors.ts` walks the chain (bounded, so a self-referencing cause terminates) and backs all 11 call sites. **General rule: never pattern-match on an ORM's thrown error by its own properties without checking what the ORM actually wraps.**
- **Under `neon-http` a read-then-write guard is not a guard.** With no transactions, `SELECT status` → decide → `UPDATE` lets two requests both pass the same read. Every lifecycle transition now claims itself with a conditional update (`UPDATE … WHERE id = $1 AND status = $expected RETURNING`) *before* doing the side-effecting work, and releases the claim if that work fails — the same idiom `decrementStockLine` already used for stock, now applied to the status machine, to absolute stock sets (`WHERE stock = $expected`), and to idempotency (a unique index). This is the house answer to concurrency here, not a per-site decision.
- **A sequence derived from `COUNT(*)` is broken by its first deletion, and its retry loop cannot recover.** Recomputing the same count on retry produces the same colliding number every attempt, so the failure is permanent rather than transient — product creation stayed dead until the row count caught back up. Sequences must come from a high-water mark (`max()` over the parsed numeric suffix) with each retry strictly advancing. Best fixed for good with a real Postgres `SEQUENCE`, which needs neither the retry nor a lock.
- **Tag-based cache invalidation cannot see the clock.** `revalidateTag` covers mutations; a promotion starting or ending is neither. Any cached value whose correctness is time-bounded needs a TTL as well as a tag, or it will keep serving a figure the server itself no longer agrees with — here, a discount the checkout would not honour. Applies to anything date-windowed added later.
- **Message-key parity between locales cannot catch a key that is missing from both.** `ar` and `fr` were at exact parity while `authErrors.invalidImageInput` — referenced by a live route — existed in neither. `tests/lib/message-keys.test.ts` now asks the other question, resolving every literal key the source references against the catalogue; it asserts its own coverage count so a refactor that breaks its binding-detection fails loudly instead of quietly checking nothing.
- **A shared CSS custom property used by two disciplines is a leak waiting to happen — give each discipline its own token, even when their values start out identical.** `globals.css`'s `@theme inline` block wired `--font-heading: var(--font-display)` — harmless while `--font-display` was Plus Jakarta Sans, but the moment the Atelier Blanc redesign repointed `--font-display` to Fraunces for the storefront, every Admin/POS page title (`font-heading text-2xl font-bold`, used on ~15 admin pages) would have silently gone serif too, since Admin and the storefront share one `globals.css`. Caught before shipping by tracing the token graph, not by visual inspection — fixed by giving `font-heading` its own independent value (set to exactly what `font-display` used to resolve to, for both `ar` and `fr`), verified with `getComputedStyle` against a real admin page rather than trusting the fix by eye. General rule: when two disciplines/surfaces are declared "independent" in DESIGN.md but share one token file, grep for every place a semantic token references *another* semantic token (not a raw value) — that reference is exactly where a future one-surface change silently becomes a two-surface change.
- Drizzle over Prisma: lighter cold starts on Vercel serverless, native fit with Neon serverless driver.
- No Redis in v1: Next.js tag-based caching + Cloudflare CDN is sufficient at expected traffic; revisit if order endpoint needs distributed rate limiting.
- Stock decrements at `confirmed` (web) / completion (POS), not at `pending`, so fake orders can't drain inventory.
- POS sales are `orders` rows with `source=pos` — one model for all revenue and one events log.
- Arabic is the default locale; French secondary.
- Env validation (`src/lib/env.ts`) runs via `instrumentation.ts` `register()` so a missing var fails at server startup, not silently at first use.
- `app/[locale]/[...rest]/page.tsx` calls `notFound()` explicitly — Next.js only renders a nested `not-found.tsx` for explicit throws, not for genuinely unmatched routes, so this catch-all is required to get the localized 404 instead of Next's built-in one.
- Sentry routing lives in `logger.ts` (keyed off `context.code`) rather than at each call site, so the "which errors reach Sentry" decision has one place to audit/test instead of being re-decided at every `logger.error` call.
- PostHog client init is deliberately decoupled from `instrumentation-client.ts` (which runs before hydration) — it's triggered from a mounted client component via `requestIdleCallback` so it can never be blamed for LCP regressions.
- Better Auth's core tables (`user`/`session`/`account`/`verification`) are modeled as `users`/`sessions`/`accounts`/`verifications` (plural, matching every other table) instead of Better Auth's singular defaults; the drizzle adapter's `usePlural: true` handles this directly, no per-table `modelName` mapping needed.
- **`db.transaction()` does not work** — `drizzle-orm/neon-http` (the HTTP, non-pooled driver `src/db/client.ts` uses) throws `Error: No transactions support in neon-http driver` at call time, even though it type-checks fine (the `.d.ts` stub exists but the runtime rejects it). Task 03's multi-step writes (create staff = insert user + insert credential account; deactivate/reset password = update + revoke sessions) run as sequential awaited statements instead, with a manual compensating delete if the second insert fails on create. Task 05's product creation (product + images + stock_movement + N variants + variant images/movements) is the same pattern, one more level deep — no compensation was added there since a failure partway through only leaves an inactive-by-default, admin-only-visible product with a partial variant set, not a customer-facing inconsistency. **This will hit task 07/07b (order creation: order + order_items + stock_movements, all customer-facing) harder** — before starting those, either switch `src/db/client.ts` to a pooled/websocket driver (`drizzle-orm/neon-serverless` + `@neondatabase/serverless`'s `Pool`, which supports real transactions) or design those flows around sequential writes with explicit compensation. Flagged here rather than fixed now since it's a cross-cutting driver choice, not an auth concern.
- **SKU numbering races under concurrent writes, and this is provable, not just theoretical**: `nextProductSkuNumber`/`nextVariantSkuNumber` (task 05) compute `count(*) + 1` against a table with no transaction to lock it. Running the new integration test file alongside the others in parallel Vitest workers reproduced real `23505` unique-violation collisions on `products_sku_unique` (a different, unrelated test file's row temporarily inflating the count). Two complementary fixes: (1) each SKU-assigning insert retries up to 5 times on a unique-violation scoped to the exact constraint name, recomputing the count fresh each attempt — cheap, correct without a lock, and the right shape for real concurrent admin writes too, not just tests; (2) `vitest.config.ts` now sets `fileParallelism: false` — this suite's integration tests share one real Neon dev-branch database (per `code-standards.md`), not an isolated instance per file, so cross-file races over shared-table aggregates are a property of the test topology, not something (1) alone should be expected to fully absorb under test-only levels of concurrency. Task 07 extracted the retry logic itself into `src/lib/sku.ts` (`insertWithUniqueSku`) so `products.ts` and `bundles.ts` share one implementation instead of two copies.
- **Running `next build` against the same `.next` directory as a live `next dev` corrupts that dev server's in-memory message cache** — discovered while manually verifying task 07 in a real browser: after `npm run build`, the already-running dev server started serving a stale copy of `messages/ar.json` specifically (missing keys added earlier in the same session; `messages/fr.json` was unaffected, apparently by luck of which chunks got touched) — server-rendered `getTranslations` calls returned raw `admin.bundles.title`-style keys instead of resolved Arabic text, logged as `next-intl` `MISSING_MESSAGE` errors even though the on-disk JSON was verified correct (`python -m json.tool` and manual inspection both confirmed it). `rm -rf .next` + restarting `next dev` fixed it immediately and permanently. Takeaway for future manual-verification passes: don't run `npm run build` while a `next dev` server you're about to browser-test is still running against the same `.next` — stop the dev server first, build, then `rm -rf .next` before restarting dev (or just skip the production-build check during an active browser-verification session and run it separately).
  **Task 09 reproduced the same class of stale-message-cache bug with a different trigger**: a `next dev` process that had already been running before `messages/{ar,fr}.json` were edited (no `next build` involved this time) kept serving the pre-edit `fr.json` specifically — `/fr/catalog` rendered `catalog.seo.title` as a raw fallback key while the same request against `/ar/catalog` (also edited, also new keys) resolved correctly, and the on-disk `fr.json` was independently confirmed correct via direct file read. Turbopack's incremental recompilation of the dynamically-`import()`-ed message module did not reliably invalidate for the locale that request hadn't touched recently. Same fix, same as above: stop the dev server, `rm -rf .next`, restart. General rule now confirmed twice, from two different triggers: **any time `messages/*.json` changes while a `next dev` server is already running, verify a fresh render of every locale you actually touched — a curl/screenshot of only one locale can pass while the other silently serves stale copy.**
- **`evaluateSession`'s split from `requireUser` (task 03) is now the template for every mutating service, not a one-off**: `createProductCore`/`updateProductCore`/`createCategoryCore`/`updateCategoryCore`/`deleteCategoryCore` take a pre-resolved `messages` object instead of calling `getTranslations` themselves, exactly like `evaluateSession` takes pre-resolved `messages` instead of calling `requireUser`. The exported `createProduct`/`updateProduct`/etc. remain the only production-reachable entry points (they resolve `requireUser` + `getTranslations` for real, then delegate) — the `*Core` functions are not a security boundary and are never called directly from a route/action, only from tests, so this doesn't create a bypass. This is what let task 05 write real integration tests (duplicate-slug `CONFLICT`, discount-`>=`-price `VALIDATION`, initial-stock `stock_movements` row) against the actual service logic, which task 03/04 couldn't do for `requireUser`-gated code at all.

Found via manual testing: `CategoryRow`'s reorder buttons (`onClick` calling `reorderCategoriesAction` directly, since there's no natural `<form>` for a pair of arrow buttons) silently succeeded server-side every time but never visibly reordered until some other action's `<form>` submission happened to also refresh the page. Fixed by awaiting the action and calling `router.refresh()` (from `@/src/i18n/navigation`) — same fix applied to `VariantRow`'s deactivate button below.
- **A `<form>` cannot nest inside another `<form>`** — `VariantRow`'s deactivate/activate button was originally its own `<form action={toggleVariantActiveAction...}>`, rendered inside `ProductForm`'s outer `<form>` (one form per product, wrapping the whole page including its variants section). Fixed the same way as the reorder-button case above: a plain `onClick` calling the bound action directly, then `router.refresh()`. General rule going forward: a row-level action rendered *inside* a page-level form (POS line items, order line edits, anything nested under task 07/14) needs the click-handler form, never a nested `<form>`.
- **Uncontrolled form fields lose their value on a failed Server Action submission — this is the same bug task 03's sign-in form hit, generalized**: any `<Input defaultValue={...}>` inside a `<form action={formAction}>` gets reset to its original `defaultValue` when the action returns a non-redirecting result (e.g. a validation `VALIDATION`/`CONFLICT` error), because the round trip re-renders the form from a fresh server payload and React does not preserve a DOM-only uncontrolled value across that. Caught by manually submitting an invalid product (discount ≥ price) and watching every other field the admin had typed vanish — not reproducible by typecheck, lint, or a unit test, only by driving the real form in a browser.

Displayed alone in a browser or composited onto a white print page this looks completely correct, which is exactly what makes it dangerous — it only breaks for a machine reader. Every luminance-based decoder that reads RGB without checking alpha (this includes `barcode-detector`'s own internal RGBA→gray conversion, and very likely a real phone/tablet camera scanner's decode path too, since alpha isn't a physical property light has) sees uniform `(0,0,0)` across the whole image and finds zero contrast — no error, just silently zero results.
